# Internationalization

## Frontend

- Messages live in `src/i18n/locales/<code>/<namespace>.json`; the file name is the top-level key (`nav.json` -> `nav.*`).
- English (`en`) is the source of truth and defines `MessageSchema`; other locales are loaded lazily.
- Adding a string: add it to the English namespace file and use `t('namespace.key')`; do not concatenate translated fragments, use placeholders.
- Adding a namespace: create `locales/en/<ns>.json`, import it and register it in `src/i18n/index.ts`, then add the file to every other locale folder.
- `src/__tests__/i18n.locale-parity.spec.ts` fails when a locale folder lacks a namespace file that English has.
- Adding a locale: create the folder with every namespace file and add it to `SUPPORTED_LOCALES` (code, label, dir).
- Backend language codes are the same BCP 47 tags as `SUPPORTED_LOCALES`.
- Format dates and numbers with the active locale (`formatMediumDate(iso, locale.value)`), not hardcoded patterns.

## Backend emails

- Transactional email catalogs: `backend/app/core/i18n/locales/<code>/email.json`.
- Catalogs are trusted source content; never build them from user input (`str.format` is applied to values).
- Three lists must agree: `core.i18n` locales, the users `Language` enum, and the catalog directories; `tests/core/test_i18n.py` fails on drift.
- A new locale therefore touches the frontend list, the backend enum, the email catalog and `HTML_LANG_BY_LOCALE`.
