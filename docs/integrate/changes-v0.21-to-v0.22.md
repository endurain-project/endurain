# Changes from v0.21 to v0.22

What changed between v0.21 and v0.22 for the people who run Endurain and for the clients that call its API. If you only use the Endurain web app on Docker, you need only the first two sections. For the rules that hold from now on, see [Compatibility between releases](compatibility.md).

## Before you upgrade

Back up the database and the `data` folder first. The upgrade cannot be undone: restoring the backup is the only way back to v0.21.

- **Upgrade from v0.21.x only, with every data migration finished.** Endurain refuses to start on a database at a revision this release does not know, which includes any database older than v0.21, before it changes anything. The error says to start the latest v0.21.x release and let it finish its upgrade and data migrations, or, for a database used by a newer release, to run that release or restore a backup taken before it. It also refuses while an install that has users still has one of the v0.21 data migrations 11, 12, 13 or 14 pending, and names the ones that have not finished. A new install has no users and is not affected.
- **On v0.20.x, go through v0.21 first.** Start the latest v0.21.x release, let its data migrations finish, then upgrade to v0.22. See [Changes from v0.20 to v0.21](changes-v0.20-to-v0.21.md).
- **The upgrade removes the v0.21 data migration records** and the table that maps the old integer ids to UUIDs. Restoring the backup is the only way back, because the downgrade is refused.
- **Existing activities are recomputed from their original files.** v0.22 computes the values a file does not record in a new way (see [How the numbers are computed](../features/activities.md#how-the-numbers-are-computed)), and after the first start it recomputes, in the background, every activity whose original file Endurain kept: uploads, bulk imports and Garmin Connect sync. Endurain is usable meanwhile, and values change as the work goes on; a restart resumes it where it stopped. The recompute replaces the values derived from the file, the streams, the laps, the workout sets and steps, and the map thumbnail when the track changed. It keeps everything you edited: name, description, private notes, type, gear, visibility and every hide setting, as well as photos, comments and links. An activity with no kept file (Strava sync keeps none) or whose file cannot be read keeps its values, and the failure is logged with the activity id. Numbers that may change, mostly where the device did not record them:
    - moving time, distance and average speed of GPS tracks, which no longer count GPS jitter at a stop;
    - maximum speed, now the fastest 5 seconds;
    - average heart rate, power and cadence, now weighted by time, with a cadence of 0 left out;
    - normalized power;
    - elevation gain and loss, and the elevation chart;
    - automatic laps, which no longer restart at a pause;
    - heart-rate zones, which now count time.
- **Multisport files imported as separate activities are grouped.** A FIT file recorded as one multisport activity (a triathlon, a duathlon) imported before v0.22 as one activity per leg becomes one multisport activity with those legs, as a new import does. The multisport activity takes the most private combination of its legs' visibility and hide settings, and every leg takes the same, so nothing becomes more visible than it was.
- **The old values cannot be brought back** except by restoring the backup, because they are overwritten.
- **A password set before v0.21 may need a reset.** Since v0.21 Endurain compares passwords in Unicode NFC form, so the same text typed on different devices is the same password. v0.21 still accepted a password stored from the raw text and quietly re-saved it in NFC form at the next sign-in; v0.22 does not. A password is affected only if it contains an accented character that was entered in decomposed form (a base letter followed by a separate accent, as some keyboards and macOS or iOS text fields produce) and the account has not signed in since v0.21. Passwords with only plain ASCII characters, or with accented characters in composed form, are not affected. The account then answers like a wrong password. The user resets it with the emailed link, or an administrator [sets a password](../features/user-management.md#resetting-a-password). See [Accounts, sign-up and password reset](../features/accounts-and-sign-in.md#password-rules).

## Environment variables that stop startup

Endurain refuses to start while any of these variables is set. It logs every variable it finds, with where the setting lives now, and stops with an error that lists them all, so you can fix the deployment in one pass. Remove them from your environment, compose file and secret files, then start again. See [Supported environment variables](../getting-started/advanced-setup.md#supported-environment-variables) for the full list.

| Variable | Where the setting lives now |
| -------- | --------------------------- |
| `ACCESS_TOKEN_EXPIRE_MINUTES`, `REFRESH_TOKEN_EXPIRE_DAYS`, `SESSION_IDLE_TIMEOUT_ENABLED`, `SESSION_IDLE_TIMEOUT_HOURS`, `SESSION_ABSOLUTE_TIMEOUT_HOURS` | *Settings > Server settings > Access & security > Sessions* |
| `READ_NOTIFICATION_RETENTION_DAYS` | *Settings > Server settings > General > Data retention* |
| `REVERSE_GEO_PROVIDER`, `PHOTON_API_HOST`, `PHOTON_API_USE_HTTPS`, `NOMINATIM_API_HOST`, `NOMINATIM_API_USE_HTTPS`, `GEOCODES_MAPS_API`, `REVERSE_GEO_RATE_LIMIT` | *Settings > Server settings > Maps & location > Reverse geocoding* (service, host, HTTPS, rate limit and API key) |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_FROM`, `SMTP_SECURE`, `SMTP_SECURE_TYPE`, `SMTP_PASSWORD`, `SMTP_PASSWORD_FILE` | *Settings > Server settings > Email* (host, port, security, username, sender and password) |
| `ALGORITHM`, `ALGORITHM_FILE` | Nowhere: tokens are always signed with HS256, so there is nothing to configure |

v0.21 saved the values of these variables (except `ALGORITHM` and `ALGORITHM_FILE`, which it ignored) into the database each time it started, so an install that ran v0.21 with a variable set already has its value stored and removing the variable loses nothing. The mail variables were saved only when `SMTP_HOST` was set, and an invalid value was skipped and the stored setting kept. Check the settings in *Settings > Server settings* after the upgrade.

## API changes

The first two affect clients of the administrator settings routes, which need the `server-settings:read` or `server-settings:write` scope.

- **`env_managed` is gone** from the answer of `GET /server-settings` and `PUT /server-settings` (`ServerSettingsAdminRead`), and from the answer of `GET /server-settings/email/settings` and `PUT /server-settings/email/settings` (`MailSettingsAdminRead`). Settings are no longer tied to environment variables, so no field is read-only for that reason. A client that reads `env_managed` must stop doing so.
- **The `409` for an environment-managed field is gone.** The two `PUT` routes used to answer `409` when the body changed a field that an environment variable set. They save the change now.
- **`If-Match` takes quoted entity tags only.** On every route that requires it, an unquoted value (`If-Match: 3`) or any other value that is not `*` or a list of quoted tags is refused with `400` and `urn:endurain:error:invalid-input`; v0.21 read `3` as `"3"`. A quoted `"*"` is an ordinary tag, not the wildcard, so it matches no version (`412`). **A client that sent the version unquoted must send the `ETag` exactly as it was read** (`If-Match: "3"`). See [Concurrent edits](errors-and-limits.md#concurrent-edits-with-etag-and-if-match).
- **`PATCH /identity-providers/{idp_id}` is a partial update.** `name` and `slug` are no longer required, and every field is optional: an omitted field keeps its stored value. A `null` for `name`, `slug`, `provider_type`, `enabled`, `scopes` or a boolean option is `422`. The rules that span fields (an `oidc` provider needs an `issuer_url` and the `openid` scope, `issuer-in-use`, `identity-provider-locked`) are checked on the stored provider with the changes applied. A client that sends the whole provider keeps working.
- **A gzipped upload names its format.** `POST /activities/upload` takes `ride.gpx.gz`, `ride.fit.gz` or `ride.tcx.gz`; a `.gz` whose name gives no supported format inside it (`ride.gz`) is `415` `urn:endurain:error:unsupported-format` at once, where it used to be accepted and then fail its job.
- **An API key whose owner is inactive is `401`.** v0.21 answered `403` `permission-denied` for a key of a deactivated account or one awaiting approval; it is now `401` with `urn:endurain:error:unauthorized` and `WWW-Authenticate: ApiKey`, like an unknown, revoked or expired key, because the key no longer authenticates anyone. See [API keys](api-keys.md).

- **Text matching is case-insensitive through a PostgreSQL ICU collation.** The activity search (`name_search`: name, town, city, country), the gear search (`nickname_contains`) and the gear nickname lookup and uniqueness compare text so that case, a Greek final sigma (`ς` equals `Σ`) and Unicode normal forms (composed equals decomposed, full-width equals ASCII) do not matter; accents and `ß` against `ss` still do. **Gear nicknames that are equal under this rule within one user were renamed by the upgrade:** the earliest acquired keeps its nickname and each other gets a numeric suffix (`Bike`, `bike (2)`), with its `version` bumped and `updated_at` stamped, so a client refetches it and `GET /sync` reports it. A `POST /gears` whose nickname equals an existing one under this rule is `409`.
- **Multisport activities.** `activity_type` has a new key, `multisport`, for an activity made of legs, and an activity carries `parent_activity_id` (read-only, `null` unless it is a leg). Lists, counts and the feed show the multisport activity and not its legs; sums run over the legs. `PATCH /activities/{activity_id}` with `activity_type` `multisport` is `422`, a `PATCH` of the type or gear of a multisport activity, or of the privacy of a leg, is `409`, and `DELETE` of a leg is `409`. A FIT file recorded as one multisport activity uploads as one `multisport` activity with its legs, and the upload job's `activity_ids` names only the multisport activity. A client that switches on `activity_type` must accept the new key. `GET /activities/{activity_id}/legs` and `GET /public/activities/{activity_id}/legs` page the legs of a multisport activity, and the activity detail carries their first page in `legs`. See [Multisport activities](data-conventions.md#multisport-activities).
- **A workout step can have no `duration_type`.** In `GET /activities/{activity_id}/workout-steps` (and the public variant) `duration_type` is `null` for a step whose FIT file names none. v0.21 refused such a file as invalid; it imports now. A client must not assume the field holds a string.
- **Recomputed activities keep their `version`.** The background recompute after the upgrade (see [Before you upgrade](#before-you-upgrade)) rewrites only server-derived values, so an activity's `ETag` stays valid; its `updated_at` is stamped, so `GET /sync` reports it and a client refetches it. A leg grouped under a multisport activity is an edit of its own: it gets its `parent_activity_id` and a new `version`.
- **Heart-rate zones count time, not samples.** In the streams' `heart_rate_zones`, `time_seconds` is the time spent in the zone and `percent` its share of the time (v0.21: the share of the samples, with the timer time split by it, and a heart rate of `0` counted in zone 1). Each sample counts the time until the next one, at most the pause threshold; a heart rate of `0` adds no time; the zone bounds are unchanged. `heart_rate_zones` is `null` when no zone holds any time.
- **Activity streams are one object on one timeline.** `GET /activities/{activity_id}/streams` and `GET /public/activities/{activity_id}/streams` no longer answer with a page of per-type streams. They answer with `offsets_ms` (the time of each sample in milliseconds from the activity start) and one list per channel (`latitude`, `longitude`, `elevation`, `heart_rate`, `power`, `cadence`, `speed`, `pace`, `temperature`), each aligned with `offsets_ms`, `null` when the activity has no such channel or hides it, plus `heart_rate_zones` (v0.21: `zone_percentages` on the heart-rate stream). Values are plain numbers with a `null` where a sample has none, and there is no `time` string any more. The per-type stream routes, their public variants and the `stream_type` values are gone; read the channel from the object. The optional `max_points` (2 to 10000) averages a longer activity into that many equal-time buckets, and `heart_rate_zones` still counts every sample. An activity that does not exist or that you may not read is now `404` (v0.21: an empty page), and an activity with no samples is `200` with an empty `offsets_ms`. `hide_start_time` no longer removes anything from the streams: the offsets count from the start and show only the duration, which the activity already shows. See [Activity streams](health-and-streams.md#activity-streams).
- **The profile archive carries samples.** A profile export writes each activity's streams as `data/activity_samples.json` (split into numbered parts for a large archive): one record per activity with its `activity_id`, `offsets_ms` and the channels, instead of `data/activity_streams.json`. An archive from v0.21 still imports; its streams are converted to samples with the restored activity's start time.
- **An effort you already have is merged, not stored twice.** An upload, a bulk import or a Garmin Connect or Strava sync of a recording that overlaps an activity of yours by at least 80% of the shorter one, in a compatible sport, returns that activity's id (v0.21: a second activity stored hidden, with a `duplicate_activity` notification) and adds the recording to it as a source. A device file (`.fit`, Garmin Connect) ranks above `.tcx` and `.gpx`, which rank above Strava; a better source that arrives later recomputes the activity in place from it (its derived values, laps, streams and start), keeping your edits, and a worse or equal one is only attached. The `ETag` and `version` stay as they were, except when the recomputed activity came only from Strava: it then takes the file's `name` and `description` and its `version` moves, so a stale write is `412`. No event is published and no activity is stored hidden. `strava_activity_id` and `garminconnect_activity_id` are read from the activity's sources, so an activity a file recorded and Strava listed shows both. A profile import skips an archived activity the account already has and counts it in `activities_skipped`.

## Idempotency keys

- **Creates accept an optional `Idempotency-Key` header.** `POST /gear-components`, `/gears`, `/health/{fasting,poop,sleep,steps,water,weight}`, `/identity-providers`, `/profile/goals`, `/users` and `/users/{user_id}/followers` answer a repeat of a request, sent with the same key, with the first answer instead of creating the record again. A request without the header behaves as before. See [Idempotency keys](idempotency.md).
- **The key is a quoted string.** The header value is an RFC 9651 Structured Field String (`Idempotency-Key: "8e03978e-40d5-43e8-bc93"`), and the bare form is refused with `400` and `urn:endurain:error:idempotency-key-invalid`. This applies to the activity upload and the archive bulk import too: **a client that sent a bare key to those routes must now quote it.**
- **A key reused for another request is `422`.** The upload and the archive bulk import answered `409` when a key came back with a different file; they answer `422` with `urn:endurain:error:idempotency-key-reused` now, as every route that takes a key does. A `409` on these routes now means a request with the key is still running (`urn:endurain:error:idempotency-key-in-flight`) or another existing conflict.

- **A sleep record holds at most 1440 stages.** `POST /health/sleep` with more `sleep_stages` is `422`, and the schema publishes `maxItems`. The limit is one stage per minute of a day, the finest granularity of a stage.

## Requirements for bare-metal and development installs

- **Python 3.15** for the backend.
- **Node.js 26** for the frontend.
- **PostgreSQL 18 built with ICU**, which the case-insensitive collation needs. The official packages and the `postgres` image include it.

The Docker image already ships both, so a Docker install needs nothing. See [Setup a development environment](../developer-guide/setup-dev-env.md).
